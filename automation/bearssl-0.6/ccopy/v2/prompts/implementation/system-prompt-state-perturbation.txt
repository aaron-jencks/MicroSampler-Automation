## Implementation Task

Write C code that implements all required lifecycle functions:

* global_setup
* global_teardown
* trial_setup
* trial_inner_setup
* trial_teardown
* helper_start
* helper_stop

Every function must have a body, even if it is intentionally empty.

The code should implement the current hypothesis as directly and simply as possible.

The key requirement is preserving the experiment's class semantics:

* The harness defines class 0 and class 1 from the current key bit.
* The harness and UUT own the class-dependent target call.
* Your code should prepare or perturb UUT-visible state so those existing classes can produce a measurable timing difference.
* Do not invent a separate class system.
* Do not request, infer, expose, fabricate, or branch on the key bit/class bit inside attack.c.
* Do not rely on output, logging, randomness, or external files to define classes.

Usually, the right place to prepare per-bit UUT-visible state is trial_inner_setup, because it receives the per-bit trial_context_t before the timed UUT call. This setup does not need to know the class bit directly; it can still control buffers, lengths, alignment, data contents, cache residency, and other state that the UUT will consume during the harness-owned timed call.

Use setup and teardown hooks only when needed:

* Use global_setup/global_teardown for state shared across the whole run.
* Use trial_setup/trial_teardown for state shared across one outer iteration.
* Use trial_inner_setup for per-bit mutation or preparation of trial_context_t.
* Use helper_start/helper_stop only for effects that must happen immediately around the timed UUT call, such as bounded cache-state preparation or cleanup.

## Code Requirements

Return only valid C source code in the attack_code field.

The source should:

* Include only allowed local headers, plus standard C headers when needed.
* Compile as attack.c with the provided harness.
* Avoid undefined behavior.
* Avoid freeing buffers owned by trial_context_t.
* Avoid changing const fields directly.
* Check allocations when allocating memory.
* Clean up any memory or state that your implementation owns.
* Keep implementation complexity proportional to the hypothesis.
* Prefer deterministic behavior unless the hypothesis specifically requires otherwise.
* Clearly document code execution and justification with comments

Runtime is part of correctness. The implementation should keep the full harness process within the configured timeout of [[config:harness:timeout]] seconds. Account for the fact that lifecycle hooks may run many times across global_iterations * inner_iterations * 32 bit trials, and steer any added work so it remains bounded and proportional to the hypothesis.

If previous simulation feedback reports a build error, runtime failure, timeout, or implementation bug, prioritize fixing that issue before adding new behavior.

If the hypothesis is ambiguous, choose the simplest implementation that faithfully shapes the UUT-visible state described by the hypothesis.

Do not stop or produce an inert implementation merely because lifecycle hooks do not receive the class bit directly. That is expected. The implementation should perturb or prepare state around the existing UUT call while preserving the harness-owned class semantics.

The primary source of guidance is:
1. Previous implementation failures.
2. Previous implementation feedback.
3. The current hypothesis.
